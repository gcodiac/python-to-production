# Lesson 11 — Secrets Manager and Kubernetes Secrets

**What you'll learn:** how the database password reaches the application without ever existing in Git, a Helm value, a ConfigMap, an environment variable, or a Kubernetes Secret.

## Goal

Trace the full path of one credential, and explain why each hop exists.

## The path

```text
RDS
 │  generates its own master password
 └── AWS Secrets Manager
           ↓  read permission granted to one ServiceAccount
      EKS Pod Identity
           ↓  temporary credentials, no keys
     Secrets Store CSI driver
           ↓  mounts as a file
      Pod filesystem  (/mnt/secrets/db_password)
           ↓  read at connection time
      application
```

## What this avoids

The common pattern is a Kubernetes Secret committed to Git:

```yaml
kind: Secret
stringData:
  password: hunter2      # now in Git history forever
```

Even without Git, a plain Kubernetes Secret is only base64-encoded (not encrypted) in etcd, and readable by anyone with `get secrets` in that namespace.

This design produces **no Kubernetes Secret at all**:

```bash
grep -A6 "syncSecret" ../infra/platform/staging/main.tf
```

`syncSecret.enabled = false` — the CSI driver *can* mirror values into Secret objects, and deliberately does not.

## SecretProviderClass

```bash
cat ../k8s/charts/notes-app/templates/secretproviderclass.yaml
```

RDS stores its managed credentials as a JSON document (username, password, host, etc.). The `jmesPath` extracts **only** the password field into its own file, so the Pod never sees the rest:

```yaml
objects: |
  - objectName: "arn:aws:secretsmanager:...:secret:..."
    objectType: "secretsmanager"
    jmesPath:
      - path: "password"
        objectAlias: "db_password"
```

The **ARN is an identifier, not a secret** — it is safe in a Helm value. Reading the secret still requires IAM permission, which only the Pod's role has.

## Mounting it

```bash
grep -B3 -A10 "db-secret" ../k8s/charts/notes-app/templates/deployment.yaml
```

Mounted `readOnly: true` at `/mnt/secrets`. The ConfigMap tells the app where to look:

```bash
grep -A3 "DB_PASSWORD_FILE" ../k8s/charts/notes-app/templates/configmap.yaml
```

## Reading it, and rotation

```bash
grep -A12 "def read_db_password" ../app/config.py
```

Read **on each connection attempt**, not cached at import. Combined with `enableSecretRotation` on the CSI driver, a rotated secret is picked up without restarting the Pod.

## A scanner false positive worth understanding

Trivy flags `KSV-0109`: *"ConfigMap stores secrets in key DB_PASSWORD_FILE"*. It matches the substring `PASSWORD`. The value is a **path** (`/mnt/secrets/db_password`), not a credential.

The name is kept anyway — the `_FILE` suffix is the established convention for passing a secret's location (the official PostgreSQL image uses `POSTGRES_PASSWORD_FILE` identically) — and the finding is documented rather than silently suppressed:

```bash
grep -A10 "id: KSV-0109" ../.trivyignore.yaml
```

This is the same triage discipline Stage 1 taught with Bandit: understand the finding, then decide, then write the decision down.

## Least privilege

```bash
grep -A12 "app_secret_read" ../infra/environments/staging/main.tf
```

`secretsmanager:GetSecretValue` on **exactly one ARN** — not `secretsmanager:*`. If the application were fully compromised, the AWS blast radius is reading a password it already legitimately holds.

## Questions for the learner

1. Why is a file mount stronger than injecting the password as an environment variable?
2. The SecretProviderClass contains a full secret ARN, committed to Git. Why is that acceptable?
3. Why read the password file per connection instead of once at startup?

## Recap

One credential, generated by RDS, stored in Secrets Manager, authorised by Pod Identity, mounted as a file by the CSI driver, and never present in Git, a ConfigMap, an env var, or etcd. Next: packaging the application itself.
